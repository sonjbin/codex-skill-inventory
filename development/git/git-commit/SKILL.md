# git-commit Skill

## 목적
- 커밋 전/중/후 체크를 표준화해서 일관된 Git 히스토리를 유지한다.

## 필수 규칙
- 전용 작업 브랜치에서만 작업한다.
- 변경은 단일 논리 목적을 유지한다. 관련 없는 변경이 섞이면 분리 제안한다.
- 사용자가 포함을 명시하지 않은 테스트용 파일, 출력(output) 파일, 실행용 셸 스크립트(`*.sh`)는 커밋 대상에서 제외한다.
- 파일 용도가 불분명하면 임의로 포함하지 말고 사용자에게 확인한다.
- 불확실하면 보수적으로 행동하고 사용자 확인을 먼저 요청한다.

## 브랜치 규칙
- 브랜치 네이밍: `<prefix>/<short-descriptive-name>`
- 허용 prefix:
  - `feature/` 신규 기능/확장
  - `fix/` 일반 버그 수정
  - `hotfix/` 긴급 수정
  - `demo/` 실험/데모

## 커밋 타입 규칙
- 권장 형식: `<type>: <summary>`
- `feat`: 새로운 기능 추가
- `fix`: 버그 수정
- `chore`: 기능/버그와 무관한 유지보수 변경(예: 의존성 업데이트)
- `refactor`: 기능 추가/버그 수정 없이 코드 구조 개선
- `docs`: README 등 문서 변경
- `style`: 코드 의미에 영향 없는 포맷/스타일 변경
- `test`: 테스트 추가 또는 기존 테스트 수정
- `perf`: 성능 개선
- `ci`: CI 파이프라인/워크플로 관련 변경
- `build`: 빌드 시스템/외부 의존성에 영향 있는 변경
- `revert`: 이전 커밋 되돌리기

## 실행 절차
1. 현재 브랜치와 변경 범위를 확인한다.
- 완료 조건: 현재 브랜치가 기본 브랜치가 아님이 확인됨.
- 검증 방법: `git branch --show-current`, `git status --short` 확인.

2. 커밋 범위가 단일 목적임을 점검한다.
- 완료 조건: 커밋 메시지 1개로 설명 가능한 변경만 포함하며, 사용자가 포함을 명시하지 않은 테스트용 파일, 출력 파일, 실행용 `*.sh` 파일은 제외됨.
- 검증 방법: `git status --short`와 `git diff --staged --name-only`의 파일 목록을 검토하고 제외 대상이 스테이징되지 않았는지 확인.

3. 커밋 메시지를 작성한다.
- 완료 조건: 변경 의도와 범위가 명확한 한 줄 요약을 포함.
- 검증 방법: 메시지 본문/제목이 변경 내용과 일치하는지 자체 점검.

4. 커밋 후 결과를 확인한다.
- 완료 조건: HEAD에 새 커밋이 생성됨.
- 검증 방법: `git log -1 --oneline` 확인.

## 중단 조건
- 브랜치가 기본 브랜치인 경우
- 변경 목적이 혼재되어 분리가 필요한 경우
- 사용자 지시와 AGENTS 규칙이 충돌하는 경우
